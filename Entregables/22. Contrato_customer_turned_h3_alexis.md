# Entregable 22 — Contrato de datos CUSTOMER y TURNED

**Responsable:** Alexis Gean Gerardo Vigo Huayán · **Hito:** H3 · **Motor:** SQL Server 2019 o posterior

## Alcance y decisiones

El plan integral asigna a Alexis la atención, el seguimiento, la agenda y las pruebas de concurrencia. Los entregables H1 acotan la evaluación docente hasta CUSTOMER. Por ello CUSTOMER es obligatorio y TURNED se entrega implementado como extensión separada, que puede omitirse en el despliegue académico sin afectar CUSTOMER. TURNED significa **seguimiento posterior a una atención**, no pérdida de un paciente. Deserción, inactividad y reactivación son estados o eventos distintos; el OLTP actual no registra una decisión formal de «paciente perdido».

| Regla | Contrato verificable |
| --- | --- |
| Grano CUSTOMER | Una fila por `Reservas.id_reserva`. Una reserva puede tener cero o una atención según el informe; si aparecen varias, se rechaza la reserva hasta resolver la anomalía. |
| Fecha de cohorte | Fecha y hora del turno de `Disponibilidad` mediante `Reservas → Opciones → Disponibilidad`. `fecha_reserva` registra creación de la reserva, no el turno. |
| Resultado explícito | Asistió si `Atenciones.asistencia = 'Asistió'` y existe `fecha_inicio` dentro del corte; no-show si `Atenciones.asistencia = 'No asistió'` o `Reservas.estado = 'No-Show'`/`'No asistió'`. No-show con inicio clínico es inconsistente y se rechaza. Cancelada y reprogramada se separan. Una cita pasada sin resultado se clasifica `PendienteResultado`; **no se inventa un no-show**. |
| Citas evaluables | Turno ya transcurrido y resultado explícito `Asistio` o `NoShow`. Futuras, canceladas, reprogramadas y pendientes de resultado no entran al denominador C1/C2. |
| C1 / C2 | `SUM(AtencionesRealizadas) / SUM(CitasEvaluables)` y `SUM(CitasConInasistencia) / SUM(CitasEvaluables)`. Se informa `NULL` si el denominador es cero. |
| C3 | `DATEDIFF(MINUTE, fecha_inicio, fecha_fin)` solo para atención finalizada con ambos tiempos válidos y `fecha_fin >= fecha_inicio`. Si el tiempo es negativo, se rechaza. La fuente `Servicios` del anexo no tiene duración objetivo; la desviación frente a objetivo queda **no disponible**. |
| C4 | Para una ficha finalizada conforme se exige `diagnostico_basico`, `procedimiento_realizado` e `indicaciones_finales`, cada uno con al menos cinco caracteres no blancos. Es la unión conservadora del checklist H1 y el informe (que difieren en los campos); el equipo debe aprobar esta definición antes de usar C4 como meta oficial. El ETL guarda solo la bandera, nunca el texto clínico. |
| Producción | No se calcula monto de producción clínica: `Opciones.precio_ofrecido` es cotización y `Servicios` no contiene tarifa estándar. No confundir con caja acreditada de PAYER. |
| PAYER → CUSTOMER | La reserva es la clave de navegación. Una atención puede ocurrir sin anticipo y una reserva puede tener múltiples pagos; ningún join a `Fact_GestionPayer` multiplica el hecho CUSTOMER. |
| Grano TURNED | Una fila por `Seguimientos.id_seguimiento`, vinculada a `id_atencion`. Se almacenan solo tipo/canal categóricos, satisfacción numérica e incidencia; no `resultado` ni `observaciones` de texto libre. |
| Retorno | Una nueva atención asistida y comenzada de la **misma persona**, posterior al seguimiento. `Retorno90Dias` se evalúa solo cuando la ventana de 90 días está completa. Por existir varios seguimientos por paciente, una tasa de pacientes recurrentes debe usar personas únicas, no sumar esta bandera sin deduplicar. |
| Historia | Las filas de hechos se actualizan en sitio cuando cambia el estado de origen. Se conserva `FechaCarga` y se añade `FechaModificacion`; este patrón no reconstruye estados históricos no guardados por OLTP. |

## Mapeo y dependencias

`staging.stg_CitasCustomer` nace de `NexoSaludDB.dbo.Reservas` y enlaza `Opciones`, `Disponibilidad`, `Solicitudes` y `Atenciones`. `staging.stg_SeguimientosTurned` nace de `Seguimientos` y enlaza `Atenciones`. Las vistas no replican DNI, antecedentes, alergias, diagnóstico, procedimiento ni notas. Las claves naturales y atributos de catálogo se resuelven contra `Dim_Tiempo`, `Dim_Hora`, `Dim_Sede`, `Dim_Servicio`, `Dim_Profesional`, `Dim_EstadoAtencion` y, si está oficializada, `Dim_Persona`. El miembro desconocido es `Key=0`; si no existe una dimensión requerida, la carga falla con un error explícito.

El DDL H2 (`8`) aún declara `Fact_AtencionCustomer` sin identificador de origen ni índice único y el script `9` hace `DELETE/INSERT`. No se deben ejecutar esos bloques de hechos **después** de instalar el ETL H3. El despliegue de los scripts `23` crea o sustituye exclusivamente los objetos CUSTOMER/TURNED de H3; no modifica los hechos BUYER, LEAD ni PAYER. La presencia de la vieja `Fact_AtencionCustomer` con filas obliga a migración revisada: el script falla en vez de borrarlas.

## Matriz de eventos y límites de agenda

| Evento de origen | Resultado analítico | Efecto |
| --- | --- | --- |
| Reserva futura confirmada, sin atención | `Futura` | Una cita programada, cero evaluables. |
| Turno pasado y asistencia explícita | `Asistio` | C1 +1 y cita evaluable +1. |
| Turno pasado y no asistencia explícita | `NoShow` | C2 +1 y cita evaluable +1, incluso sin fila en `Atenciones`. |
| Turno pasado sin resultado | `PendienteResultado` | Alerta de calidad; no se imputa asistencia ni no-show. |
| Reserva cancelada o reprogramada | `Cancelada`/`Reprogramada` | Excluida del denominador, visible para auditoría. |
| Dos atenciones para una reserva | `Rechazada` | Error de cardinalidad; se registra motivo. |
| Fin anterior al inicio | `Rechazada` | No se calcula duración negativa. |
| Seguimiento con atención fuente inexistente | `Rechazada` | No se inventa paciente ni atención. |

La tabla `Reservas` no contiene un historial de reprogramación ni una restricción que impida dos reservas activas para la misma `id_disponibilidad`. El script de auditoría `25` detecta estas colisiones. `25. Reserva_segura_oltp_h3.sql` implementa el camino transaccional mediante bloqueo de aplicación, comprobación de reservas activas e inserción atómica; la batería prueba dos sesiones simultáneas. El endpoint `POST /api/lead/:id/reserve` debe invocar ese procedimiento o adoptar una transacción equivalente. Como el backend no está en este repositorio, no se declara integrada esa ruta.

## Criterios de aceptación

1. Dos ejecuciones con mismo corte dan el mismo número de hechos y las mismas medidas; la segunda reporta filas sin cambio.
2. `COUNT` de reservas dentro del corte = `SUM(CitasProgramadas)` vigente + rechazos del lote. Una fila antes válida y ahora rechazada permanece neutralizada (`CitasProgramadas=0`) para conservar linaje; nunca suma KPI.
3. No-show explícito sin atención permanece en el hecho y contribuye a C2.
4. Citas futuras, canceladas y sin resultado no inflan C1/C2.
5. Fechas invertidas, cardinalidad rota y seguimiento huérfano generan rechazos trazables.
6. Una persona con dos atenciones conserva identidad; un seguimiento genera a lo sumo una fila TURNED.
7. La conciliación por reserva y los KPIs no suman pagos varias veces.

**Estado de validación:** diseño y scripts ejecutables en entorno aislado. La conexión a un mart real, las reglas definitivas de C4 y TURNED, la duración objetivo por servicio y la solución transaccional de doble reserva requieren acuerdo o fuente externa.
