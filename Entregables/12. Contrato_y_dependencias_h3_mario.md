## 3. Contrato de Datos Propuesto para BUYER y LEAD

### 3.1 Contrato Fact_CaptacionBuyer (Grano: 1 Fila por Persona Registrada)
* **Unidad de Análisis:** Cada paciente o contacto registrado en `NexoSaludDB.dbo.Personas` (`id_persona`).
* **Propósito:** Medición de volumen de captación, calidad registral, cumplimiento LPDP y conversión inicial a solicitud formal.
* **Manejo de Recurrencia:** La persona conserva su fila única en `Fact_CaptacionBuyer`. Consultas posteriores no crean nuevas filas Buyer ni alteran la fecha original de captación.
* **Compatibilidad de Claves Temporales:** Se define `KeyTiempoRegistro` (formato entero `YYYYMMDD`) y se expone `KeyTiempo` mediante alias/vista para mantener compatibilidad con reportes preexistentes.

```sql
-- DDL Propuesto: dbo.Fact_CaptacionBuyer
CREATE TABLE dbo.Fact_CaptacionBuyer (
    KeyFactBuyer                BIGINT IDENTITY(1,1) NOT NULL,
    id_persona_origen           INT NOT NULL,                           -- Natural Key de Idempotencia
    KeyTiempoRegistro           INT NOT NULL,                           -- Formato YYYYMMDD (Fecha Registro)
    KeyTiempoConversion         INT NOT NULL DEFAULT 0,                 -- Formato YYYYMMDD (0 si no convirtió a LEAD)
    KeyCanal                    INT NOT NULL DEFAULT 0,                 -- Clave foránea Dim_Canal (0 si no especificado)
    KeyFuente                   INT NOT NULL DEFAULT 0,                 -- Clave foránea Dim_Fuente (0 si no especificada)
    KeyCampana                  INT NOT NULL DEFAULT 0,                 -- Clave foránea Dim_Campana (0 si orgánico / sin campaña)
    KeySede                     INT NOT NULL DEFAULT 0,                 -- Clave foránea Dim_Sede (0 si no asignó sede en registro)
    KeyPersona                  INT NOT NULL DEFAULT 0,                 -- Clave foránea Dim_Persona (0 si no conformada)
    KeyEstadoRegistro           INT NOT NULL DEFAULT 0,                 -- Clave foránea Dim_EstadoRegistro (Válido, Incompleto, etc.)
    
    -- Métricas Aditivas (Compatibles con report.routes.ts y evaluación B1/B2/B3)
    ContactosRegistrados        INT NOT NULL DEFAULT 1,                 -- Métrica base (siempre 1 por persona)
    ContactosUtilizables        INT NOT NULL DEFAULT 0,                 -- 1 si Calidad='Valido' Y AutorizaContacto=1
    ContactosElegiblesB1        INT NOT NULL DEFAULT 0,                 -- Denominador B1: 1 si es utilizable Y cumplió madurez temporal >= 14 días respecto al corte
    ConversionesALead14Dias     INT NOT NULL DEFAULT 0,                 -- Numerador B1: 1 si pertenece a ContactosElegiblesB1 Y convirtió en <= 14 días exactos

### 3.4 Mecanismo de Actualización Completa (Idempotencia, Transacciones y Concurrencia)

> **Nota Metodológica:** Los siguientes bloques T-SQL constituyen un **patrón arquitectural ilustrativo de diseño lógico** para orientar la construcción del pipeline de Mario. No representan un script ejecutable de despliegue en esta fase de análisis.

El pipeline debe detectar cualquier diferencia relevante entre el estado del staging y la tabla de hechos mediante comparaciones booleanas estrictas (sin usar valores centinela como `-999` que puedan confundirse con datos válidos), cubriendo:
1. Transición de valores nulos a no nulos (ej. `MinutosPrimeraRespuesta`, `SegundosPrimeraRespuesta`, `TiempoConversionDias`, `PrecioCotizado`).
2. Respuestas tardías que no cumplieron el SLA (donde `SegundosPrimeraRespuesta` pasa de `NULL` a un valor $> 900$, actualizando el estado a `'Incumplida'` sin alterar el numerador `LeadsRespuestaUtil15Min = 0`).
3. Correcciones inversas o cancelaciones operativas (ej. una reserva eliminada o rechazada en OLTP que revierte `LeadsConvertidosPayerTotal` de 1 a 0).
4. Maduración de cohortes (solicitudes que cumplen los 14 días y transitan de `CohorteInmadura = 1` a `LeadsCohorteEvaluable = 1`).
5. Actualización tardía de dimensiones conformadas (`KeyCampana` y `KeyPersona` en BUYER, y `KeyPersona` en LEAD) cuando estas se resuelven en fases posteriores del Mart.
6. Cambios en dimensiones asignadas (reasignación de `KeyNegociador`, cambio de `KeySede` o actualización de `KeyServicio`).

        f.KeyTiempoConversion <> stg.KeyTiempoConversion

END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
    THROW;
END CATCH;
```

#### C. Límites del Patrón UPSERT sobre Filas Mutables vs. Historia Inmutable
> [!WARNING]
> **El UPSERT sobre una Fila Mutable NO Produce Historia Inmutable:**  
> El patrón de inserción y actualización (*Upsert*) propuesto actualiza el registro analítico en el lugar (*in-place*). Si una solicitud transita de `'En Negociacion'` a `'Confirmada'`, `'Cancelada'` o `'Abandonada'`, los campos de la fila de hechos en `Fact_NegociacionLead` son sobrescritos para reflejar el estado más reciente disponible.  
> Por tanto, **este mecanismo no crea una historia inmutable ni preserva los estados intermedios que la entidad atravesó a lo largo del tiempo**.  
> 
> * **Diseño Adicional Requerido:** Si la clínica requiriera reconstrucción histórica exacta a cualquier punto del tiempo (*as-was analysis*), se requeriría un diseño arquitectural complementario, tal como:
>   1. Tablas de **Snapshots Periódicos de Hechos** (fotos estáticas acumulativas al cierre de cada semana o mes).
>   2. Hechos o dimensiones modelados bajo **SCD Tipo 2 / Bi-temporalidad** (con `FechaInicioValidez`, `FechaFinValidez` y bandera `EsRegistroActual`).
> * **Límite Estructural de Recuperación:** Se subraya que ningún mecanismo de versionado o snapshot en el Data Mart puede recuperar retroactivamente cambios o transiciones intermedias no capturadas si el sistema operativo de origen (`NexoSaludDB`) ya los sobrescribió o purgó físicamente sin conservar una bitácora transaccional previa.

## 4. Especificaciones Temporales, Cohortes y SLAs

### 4.1 Instante de Evaluación, Fecha de Reporte y Comparaciones Directas
* **Separación Conceptual de Parámetros:**
  * **Fecha de Reporte (`@FechaCorte DATE`):** Día calendario al que se refiere el análisis (ej. `2026-09-30`).
  * **Instante de Evaluación (`@InstanteEvaluacion DATETIME2`):** Momento exacto de corte temporal. Para un reporte que evalúa hasta el final de `@FechaCorte`, el instante de corte estricto es el inicio del día siguiente:
    $$\text{@InstanteEvaluacion} = \text{DATEADD(day, 1, CAST(@FechaCorte AS DATETIME2))}$$
* **Límites con Comparaciones Directas (Sin DATEDIFF Entero):**  
  Se prohíbe el uso de `DATEDIFF(day, ...)` entero para decidir los límites exactos de una ventana de 14 días. `DATEDIFF(day, ...)` cuenta únicamente transiciones de medianoche y no lapsos de 24 horas continuas (un evento ocurrido a las 23:50 y otro al día siguiente a las 00:10 arroja `DATEDIFF = 1` cuando solo transcurrieron 20 minutos; igualmente, un evento que dista 14 días y 6 horas puede computar como 14 días pese a exceder el plazo).
  
  La pertenencia estricta a la ventana de 14 días se evalúa mediante comparación directa de timestamps:
  ```sql
  WHERE fecha_conversion >= fecha_inicio
    AND fecha_conversion <= DATEADD(day, 14, fecha_inicio)
    AND fecha_conversion < @InstanteEvaluacion
  ```
  Cualquier evento con timestamp mayor o igual a `@InstanteEvaluacion` queda estrictamente excluido del cálculo analítico de dicho corte.

* **Distinción de Hitos en el Proceso de Reserva y Conversión:**
  Para evitar ambigüedades entre las etapas comerciales y financieras, se diferencian tres momentos independientes:
  1. **Creación de Reserva (`Reservas.fecha_reserva`):** Registro del compromiso comercial inicial del paciente con turno y sillón dental asignados en estado operativo `'Pendiente'`.
  2. **Confirmación Explícita (`Reservas.fecha_confirmacion` y `Reservas.confirmacion_explicita = true`):** Acreditación explícita de confirmación de asistencia o cierre formal de la reserva en el aplicativo.
  3. **Validación del Pago (`Pagos.fecha_validacion` con `estado = 'VALIDADO'` / `'VALIDATED'`):** Conciliación bancaria efectiva del pago en la etapa PAYER (Hito H4).
  * **Propuesta Técnica Provisional:** Para la etapa LEAD (Hito H3 de Mario), se propone como hito de conversión comercial a reserva la **fecha de creación de la reserva** (`Reservas.fecha_reserva`), asumiendo provisionalmente que el lead se convirtió en el momento en que formaliza el turno. Se deja explícito que **la elección de contar una reserva pendiente como conversión definitiva es una propuesta técnica pendiente de validación colegiada con el responsable de PAYER (Jesús Daniel Ordóñez Ugarte, Integrante 4, cuyo rol será asumido posteriormente por Mario según el intercambio comunicado; Anthony Garcia Ventura es el Integrante 7 responsable de infraestructura y datos operativos), no una decisión formal cerrada del equipo**. Si el equipo determina que la conversión solo existe con confirmación explícita (`fecha_confirmacion`) o pago validado, el cálculo en staging se adaptará sin fricción.

* **Estado de la Zona Horaria:** No se debe afirmar que `DATETIME2` garantice hora local de Trujillo. En SQL Server, `DATETIME2` carece de información de zona horaria (*timezone-agnostic*). Dado que Prisma y Node.js manejan timestamps estándar en UTC mientras los entornos de base de datos pueden operar en UTC-5 local, la convención exacta del origen queda catalogada como **pendiente de homologación técnica**. Por ello, se deben evitar cálculos dependientes de `GETDATE()` en la capa de extracción/staging, calculando métricas temporales frente a parámetros de evaluación deterministas.

* **Límites de Reconstrucción Histórica:** En `NexoSaludDB`, tablas transaccionales como `Personas` y `Solicitudes` sobrescriben su estado comercial (`estado`, `id_etapa_actual`, `fecha_actualizacion`) sin un registro inmutable completo de transiciones previas (solo existen eventos parciales en `EventosEtapa`). Reconstruir el estado de un lead a una fecha de corte pasada posee limitaciones estructurales insalvables sin un historial de auditoría OLTP.

### 4.2 Maduración de Cohortes y Elegibilidad Rigurosa (B1 y L1)

Se prohíbe terminantemente en todo el modelo la formulación híbrida de elegibilidad *"maduró O convirtió"*.

#### A. Principio Metodológico de Cohorte Madura Cerrada:
Para cualquier cálculo de tasa de conversión sobre cohortes maduras, **el numerador y el denominador deben nutrirse exclusivamente de la misma población temporalmente madura**, independientemente de si los individuos convirtieron o no:
* **Denominador de Cohorte Madura:** Únicamente registros cuya fecha de inicio tiene al menos 14 días continuos transcurridos respecto al corte temporal:
  $$\text{fecha\_inicio} \le \text{DATEADD(day, -14, @InstanteEvaluacion)}$$
* **Numerador de Cohorte Madura:** Exclusivamente aquellos registros pertenecientes a dicho denominador maduro cuya conversión formal ocurrió en el intervalo exacto:
  $$\text{fecha\_conversion} \ge \text{fecha\_inicio} \quad \text{AND} \quad \text{fecha\_conversion} \le \text{DATEADD(day, 14, fecha\_inicio)}$$
* **Tratamiento de Conversiones Tempranas:** Si un contacto o solicitud ingresó hace 4 días y ya formalizó reserva en el día 2, dicha conversión se conserva en las columnas operativas del hecho (`ConversionesALead = 1`, `LeadsConvertidosPayerTotal = 1` y con la fecha correspondiente en `KeyTiempoReserva`), pero **no se incorpora anticipadamente a la cohorte madura cerrada** (`LeadsCohorteEvaluable = 0`, `LeadsConvertidosPayer14Dias = 0`) hasta que toda su cohorte agote la ventana temporal completa.

#### B. Distinción entre Madurez Individual y Cierre de Cohorte Mensual:
* **Madurez Individual:** Cada registro madura individualmente según su fecha particular (`fecha_inicio <= DATEADD(day, -14, @InstanteEvaluacion)`).
* **Cierre Completo de una Cohorte Mensual:** Para evaluar la tasa de conversión cerrada del mes de Septiembre de 2026, no basta con evaluar el 30 de septiembre; se requiere que el último registro ingresado (30 de septiembre a las 23:59) haya completado sus 14 días continuos. Por ende, la cohorte mensual de septiembre solo se declara formalmente **madura y cerrada** a partir del **15 de octubre de 2026**:
  $$\text{@InstanteEvaluacion} \ge \text{2026-10-15 00:00:00}$$

> [!IMPORTANT]
> **Ejemplo de Distorsión Metodológica Evitada (14 Días Continuos):**  
> La ventana de maduración comprende **14 días continuos (336 horas)**, no días hábiles. Cada registro madura individualmente según su fecha particular. Por su parte, el cierre completo de una cohorte mensual requiere esperar a que culmine la ventana de 14 días continuos de todo el período (por ejemplo, el 15 de octubre para la cohorte de septiembre).  
> Si durante los últimos 3 días ingresaron 10 solicitudes formales y 2 de ellas reservaron de inmediato, esas 10 solicitudes **no constituyen una cohorte cerrada ni justifican publicar una tasa del 100 % de conversión** (considerando solo las 2 convertidas prematuramente) **ni una tasa distorsionada del 20 %** (al penalizar 8 solicitudes que aún disponen de 11 días continuos para convertir).  
> Las 10 solicitudes se mantienen clasificadas con `CohorteInmadura = 1` y `LeadsCohorteEvaluable = 0` hasta que cada una cumpla sus 14 días continuos, momento en el cual ingresan al denominador para reflejar la tasa madura real de la cohorte.

### 4.3 Medición de Primera Respuesta Útil en $\le 15$ Minutos Hábiles (KPI L2)

* **Precisión Suficiente de Duraciones:**  
  Para distinguir con rigor un lapso de 15 minutos exactos de uno de 15 minutos y algunos segundos, las duraciones de respuesta se calculan y almacenan en **segundos hábiles** (`SegundosPrimeraRespuesta INT`):
  $$\text{Umbral de Cumplimiento L2} = \text{SegundosPrimeraRespuesta} \le 900 \text{ segundos}$$
  Si una respuesta tarda 910 segundos (15 minutos y 10 segundos), se clasifica como incumplimiento de SLA (`LeadsRespuestaUtil15Min = 0`). La columna `MinutosPrimeraRespuesta` se conserva como métrica derivada para visualización ejecutiva.

* **Presentación de Solicitudes y Separación de Casos en L2:**  
  Para evitar sesgos y no distorsionar el cumplimiento operativo, el universo de solicitudes se desagrega en cuatro categorías transparentes:
  1. **Solicitudes que Requieren Respuesta (`LeadsRequierenRespuesta = 1`):** Universo total de solicitudes formalizadas que demandan atención comercial.
  2. **Pendientes Dentro del Plazo (`EstadoRespuestaSLA = 'PendienteDentroSLA'`):** Solicitudes en curso sin respuesta registrada cuyo tiempo hábil transcurrido al `@InstanteEvaluacion` es $\le 900$ segundos. No se penalizan ni se computan como incumplimiento prematuro.
  3. **Evidencia Insuficiente o No Concluyente (`EstadoRespuestaSLA = 'EvidenciaInsuficiente'`):** Solicitudes donde la ausencia de trazabilidad en `Interacciones` o la presencia de múltiples solicitudes abiertas concurrentes impide acreditar o descartar fehacientemente la respuesta útil. **Bajo ninguna circunstancia se debe declarar incumplimiento acreditado únicamente porque falta evidencia** (la ausencia de registro en el backend no demuestra que el operador no haya respondido). Estos casos se aíslan para auditoría de calidad de datos y se reporta la tasa de cobertura de evidencia.
  4. **Casos Evaluables para SLA:** Solicitudes que cuentan con evidencia verificable para dirimir formalmente el indicador:
     * *Cumplimiento Acreditado (`LeadsRespuestaUtil15Min = 1`):* Respuesta útil trazable con `SegundosPrimeraRespuesta <= 900`.
     * *Incumplimiento Acreditado (`LeadsRespuestaUtil15Min = 0`):* Respuesta útil trazable que superó los 900 segundos hábiles, o solicitud que agotó el horario hábil permitido sin respuesta antes del corte, o solicitud cerrada/abandonada sin respuesta.
* **Tasa Definitiva Pendiente de Validación:** Dado que la clínica Luxedent no cuenta con un horario hábil oficial ni una política de SLA formalmente validados por el sponsor (existiendo discrepancias entre el código y las semillas), **la tasa definitiva de L2 se mantiene clasificada como provisional y pendiente de aprobación colegiada**.

### 4.4 Tasa de Abandono sobre Resultados Finales (KPI L3)
* **Principio de Exclusión Mutua:** Una solicitud finalizada no puede computarse simultáneamente como convertida y como abandonada.
* **Denominador Formal (`LeadsResultadoFinal`):** Únicamente solicitudes que alcanzaron un estado resolutivo definitivo:
  $$\text{LeadsResultadoFinal} = \text{LeadsConvertidosPayerTotal} + \text{LeadsAbandonados}$$
* **Fórmula Oficial:**
  $$\text{Tasa de Abandono (L3)} = \frac{\sum \text{LeadsAbandonados}}{\sum \text{LeadsResultadoFinal}} \times 100$$
  Solicitudes en negociación (`LeadsEnNegociacion = 1`) no ingresan al denominador de abandono.

* PKs subrogadas (`BIGINT IDENTITY`) y restricciones `UNIQUE` sobre claves naturales de origen (`id_persona_origen`, `id_solicitud_origen`).
* Adopción de Smart Key `YYYYMMDD` en `Dim_Tiempo` (alineada con `etl_populate_mart.sql`) y `-1` como desconocido en `Dim_Hora`.
* Incorporación obligatoria de `LeadsResultadoFinal` para compatibilidad con consumidores analíticos.
* Sustitución del `DELETE` masivo destructivo por el patrón de Upsert transaccional idempotente.
* Denominador de L3 restringido exclusivamente a solicitudes con resultado final mutuamente excluyente.
* Cálculo de cohortes maduras cerradas nutriendo numerador y denominador exclusivamente de la población temporalmente madura.

### 7.2 Decisiones que Requieren Validación del Equipo
* Horario hábil oficial de la clínica para el cálculo determinístico de segundos/minutos de respuesta en L2.
* Aprobación del algoritmo de proximidad temporal en staging con consumo 1:1 de interacciones.
* Criterio de imputación de costos de marketing (distinción entre campañas sin costo vs campañas con costo no registrado).
* Homologación de convención horaria entre Node/Prisma y SQL Server.

### 7.3 Fuentes o Recursos Todavía Faltantes
* Migración de Prisma o script DDL que incorpore `id_solicitud` en `Interacciones`.
* Endpoint de backend que persista en tiempo de ejecución la fecha de primera respuesta útil en `Solicitudes`.
* Confirmación del sponsor sobre la jornada asistencial de atención al cliente de Luxedent en Trujillo.

### 7.4 Trabajo de Staging que Puede Prepararse de Forma Autónoma
* Construcción de la vista de staging `stg_Personas`: normalización interna de celulares peruanos equivalentes antes del hash sin exponer teléfonos en la proyección pública, derivación de hashes (`NULL` para vacíos), banderas separadas de presencia (nombres, apellidos, contacto), formato y contactabilidad técnica, evitando cálculos volátiles dependientes de `GETDATE()`.
* Construcción de la vista de staging `stg_Solicitudes`: normalización de estados de solicitud (incluyendo `'Convertida'` y preservando `'Cancelada'` y `'Descartada'`), derivación estricta de banderas desde un único estado normalizado, detección de contradicciones fecha-estado, primer precio y primera reserva deterministas por orden cronológico e ID.
* Construcción de `stg_Interacciones` con exclusión de textos libres (`resultado_original` y `resultado_norm`) y categorización cerrada segura.
* Construcción de `stg_EventosEtapa` mediante `LEFT JOIN` a `dbo.Etapas` usando nombres del catálogo OLTP (`TURNED`, sin inventar `ADVOCATE`).
