## 1. Introducción y Estándares de Transformación de Datos

El presente documento constituye la especificación canónica y exhaustiva de **linaje, transformación, limpieza y mapeo de datos** que conecta la base de datos relacional operativa (`NexoSaludDB`) con el almacén analítico dimensional (`NexoSalud_Mart`).

Este catálogo de mapeo define la lógica que deberán implementar estrictamente los **Integrantes 3, 4 y 5** en el desarrollo de los procedimientos de extracción, transformación y carga (ETL) durante el Hito H3.

### 1.1 Reglas Globales de Limpieza y Normalización
1. **Tratamiento de Nulos y Claves Huérfanas:**
   * En ninguna tabla de hechos se permiten claves foráneas (`FK`) con valor `NULL`.
   * Si en la base operativa el valor de una clave foránea es nulo (ej. `id_campana_origen IS NULL` en `Personas`), el pipeline ETL debe mapear obligatoriamente dicha referencia hacia la llave subrogada `0` (`KeyCampana = 0`, correspondiente a `'Sin Campaña / Tráfico Directo'`).
2. **Normalización de Cadenas de Texto:**
   * Toda comparación de literales se efectúa previa aplicación de `UPPER(TRIM(...))`.
   * Se remueven caracteres invisibles, saltos de línea y tabulaciones de los descriptores de texto.
3. **Conversión y Casting Temporal (Zona Horaria America/Lima - UTC-5):**
   * Las fechas operativas almacenadas en formato `DATETIME2(7)` se transforman al formato estándar de clave sustituta entera:
     $$\text{KeyTiempo} = \text{CONVERT}(\text{INT}, \text{CONVERT}(\text{CHAR}(8), \text{fecha}, 112)) \quad \longrightarrow \quad \text{Formato YYYYMMDD}$$
   * Las horas se transforman al formato entero de cuatro dígitos:
     $$\text{KeyHora} = \text{DATEPART}(\text{HOUR}, \text{fecha}) \times 100 + \text{DATEPART}(\text{MINUTE}, \text{fecha}) \quad \longrightarrow \quad \text{Formato HHMM}$$
4. **Protección de Confidencialidad y Datos Sensibles (LPDP Ley 29733):**
   * Se prohíbe la transferencia de campos de texto libre médico (`alergias`, `antecedentes`, `evaluacion`, `diagnostico_basico`, `observaciones`) hacia el Data Mart.
   * La identidad del paciente en el Mart se aísla mediante clave subrogada `KeyPersona`, manteniendo el vínculo transaccional exclusivamente mediante `id_persona_origen`.

### 2.1 Dimensión Tiempo (`Dim_Tiempo`)
* **Naturaleza:** Dimensión Conformada Maestra generada proceduralmente (SCD Tipo 0).
* **Granularidad:** 1 fila por cada fecha única de interacción clínica y transaccional.
* **Clave Primaria:** `KeyTiempo INT IDENTITY(1,1) PRIMARY KEY`. Clave natural de cruce: `id_fecha DATE NOT NULL`.

| Columna Destino Mart | Tipo de Dato Mart | Origen / Lógica de Transformación | Descripción Funcional y Reglas |

| **`KeyTiempo`** (PK) | `INT IDENTITY(1,1)` | Autonumérico secuencial | Llave primaria subrogada artificial de la dimensión. |

### 3.1 `Fact_CaptacionBuyer` (Fase 1: BUYER)
* **Grano:** 1 persona/contacto registrado en `NexoSaludDB.dbo.Personas`.
* **Llave Primaria:** `KeyFactBuyer BIGINT IDENTITY(1,1) PRIMARY KEY CLUSTERED`
* **Restricción de Idempotencia:** `UNIQUE NONCLUSTERED (id_persona_origen)`

| Columna Destino Mart | Tipo de Dato | Tabla / Campo Origen OLTP | Lógica de Transformación / Cálculo de Métricas |
| :--- | :--- | :--- | :--- |
| **`id_persona_origen`** | `INT NOT NULL` | `p.id_persona` | Clave primaria del contacto en OLTP. |
| **`KeyTiempoRegistro`** | `INT NOT NULL` | `p.fecha_registro` | `CONVERT(INT, CONVERT(CHAR(8), p.fecha_registro, 112))`. |
| **`KeyTiempoConversion`**| `INT NOT NULL` | Primer evento a LEAD | `COALESCE(CONVERT(INT, CONVERT(CHAR(8), s.fecha_primera_solicitud, 112)), 0)`. |
| **`KeyCanal`** | `INT NOT NULL` | `p.id_canal_origen` | `COALESCE(dc.KeyCanal, 0)`. |

## 4. Resumen de Roles Temporales y Guía para Integrantes 3, 4 y 5

Para evitar confusiones analíticas en los reportes de Power BI, se consolida la guía de roles temporales que los Integrantes 3 al 5 deben aplicar en sus consultas de carga:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        MAPEO DE ROLES TEMPORALES EN FACT TABLES                        │
├────────────────────────┬──────────────────────────┬────────────────────────────────────┤
│ Tabla de Hechos        │ Columna en Mart          │ Origen en Transaccional (OLTP)     │
├────────────────────────┼──────────────────────────┼────────────────────────────────────┤
│ Fact_CaptacionBuyer    │ KeyTiempoRegistro        │ Personas.fecha_registro            │
│                        │ KeyTiempoConversion      │ Solicitudes.fecha_solicitud (Min)  │
├────────────────────────┼──────────────────────────┼────────────────────────────────────┤
│ Fact_NegociacionLead   │ KeyTiempoSolicitud       │ Solicitudes.fecha_solicitud        │
│                        │ KeyTiempoReserva         │ Reservas.fecha_reserva             │
├────────────────────────┼──────────────────────────┼────────────────────────────────────┤
│ Fact_GestionPayer      │ KeyTiempoPago            │ Pagos.fecha_registro               │
│                        │ KeyTiempoValidacion      │ Pagos.fecha_validacion             │
│                        │ KeyHora                  │ Pagos.fecha_registro (HHMM)        │
├────────────────────────┼──────────────────────────┼────────────────────────────────────┤
│ Fact_AtencionCustomer  │ KeyTiempoAtencion        │ Atenciones.fecha_atencion          │
│                        │ KeyHora                  │ Atenciones.fecha_atencion (HHMM)   │
└────────────────────────┴──────────────────────────┴────────────────────────────────────┘
```

Con estas matrices contractuales cerradas, el diseño dimensional garantiza consistencia total y sienta las bases para el DDL y los scripts de población del Data Mart.
