## Orden de despliegue

1. Tener los objetos OLTP de `Contexto/Anexos.md` y el mart con dimensiones conformadas. Resolver primero la brecha `Dim_Persona`: el DDL H2 original no la crea, pero los ETL H3 de BUYER, LEAD y PAYER la requieren. Todas las dimensiones usadas deben tener `Key=0` y las claves naturales cargadas.
2. Tener `dbo.Log_Ejecucion_ETL` creada por el ETL BUYER (`15`) y los ETL previos que se quieran integrar.
3. No ejecutar el DDL H2 (`8`) ni la carga masiva (`9`) sobre un mart que ya contiene hechos H3. Si hay filas en la estructura CUSTOMER H2, migrarlas bajo revisión antes de instalar el hecho nuevo; el script detiene ese caso.
4. Desde la raíz del repositorio, conectado al mart de desarrollo:

```powershell
sqlcmd -S '(localdb)\MSSQLLocalDB' -E -d NexoSalud_Mart -b -f 65001 -v OLTP_DB=NexoSaludDB -i 'Entregables\22. Staging_customer_turned_h3.sql'
sqlcmd -S '(localdb)\MSSQLLocalDB' -E -d NexoSalud_Mart -b -f 65001 -i 'Entregables\23. ETL_Fact_AtencionCustomer_h3.sql'
sqlcmd -S '(localdb)\MSSQLLocalDB' -E -d NexoSalud_Mart -b -f 65001 -i 'Entregables\23. ETL_Fact_SeguimientoTurned_h3.sql'
```

Para una entrega docente acotada a CUSTOMER, omitir el tercer script. El procedimiento de reserva se instala por separado **en el OLTP** y solo protege las rutas que lo invoquen:

```powershell
sqlcmd -S '(localdb)\MSSQLLocalDB' -E -d NexoSaludDB -b -f 65001 -i 'Entregables\25. Reserva_segura_oltp_h3.sql'
```

Los nombres de bases pasados a `-v` deben ser identificadores SQL confiables, no entrada de un usuario final.

## Ejecutar cargas

```sql
DECLARE @I INT,@A INT,@S INT,@R INT,@P INT;
EXEC dbo.usp_Cargar_Fact_AtencionCustomer
 @FechaCorte='2026-10-22',@BatchId='CUSTOMER-20261022',
 @Insertados=@I OUTPUT,@Actualizados=@A OUTPUT,@SinCambio=@S OUTPUT,
 @Rechazados=@R OUTPUT,@Pendientes=@P OUTPUT;
SELECT @I Insertados,@A Actualizados,@S SinCambio,@R Rechazados,@P Pendientes;
-- Si el alcance incluye TURNED, ejecutar después con el mismo contrato de parámetros.
```

`@Pendientes` significa citas vencidas sin resultado en CUSTOMER; en TURNED significa cohortes que aún no cumplen 90 días. Cada procedimiento usa bloqueo exclusivo por aplicación, índice natural único, actualización en sitio, `BatchId`, bitácora `INICIO/EXITO/ERROR` y una tabla propia de rechazos. Ejecutar una segunda vez con nuevo `BatchId` y mismo corte debe dejar `Insertados=0`, `Actualizados=0` y el mismo número de hechos.

## Consultas para Jeanfranco y conciliación

```sql
SELECT KeyTiempoTurno,KeySede,KeyServicio,
 SUM(CitasEvaluables) AS Denominador,
 SUM(AtencionesRealizadas) AS NumeradorC1,
 SUM(CitasConInasistencia) AS NumeradorC2,
 100.0*SUM(AtencionesRealizadas)/NULLIF(SUM(CitasEvaluables),0) AS C1_Porcentaje,
 100.0*SUM(CitasConInasistencia)/NULLIF(SUM(CitasEvaluables),0) AS C2_Porcentaje,
 SUM(CitasVencidasSinResultado) AS CalidadPendiente
FROM dbo.Fact_AtencionCustomer
GROUP BY KeyTiempoTurno,KeySede,KeyServicio;

SELECT 1.0*SUM(COALESCE(TiempoEnSillonDentalMin,0))/NULLIF(SUM(AtencionesFinalizadas),0) AS C3_MinutosPromedio,
 100.0*SUM(AtencionesFinalizadasConformes)/NULLIF(SUM(AtencionesIniciadas),0) AS C4_Porcentaje
FROM dbo.Fact_AtencionCustomer;

SELECT COUNT(*) AS Seguimientos,
 SUM(Cohorte90DiasEvaluable) AS CohortesMaduras,
 SUM(Retorno90Dias) AS SeguimientosConRetorno90Dias
FROM dbo.Fact_SeguimientoTurned;
```

El indicador de retorno anterior está a **grano seguimiento**. Para «porcentaje de pacientes que retornan», usar personas distintas y una cohorte de pacientes definida. No relacionar dos hechos directamente ni sumar importes de PAYER después de hacer join con CUSTOMER. PAYER tiene grano pago; CUSTOMER tiene grano reserva. Caja validada y producción clínica deben mostrarse separadas.

## Pruebas y límites

Ejecutar `powershell -ExecutionPolicy Bypass -File 'Entregables\24. ejecutar_pruebas_alexis.ps1'` en un entorno de desarrollo con LocalDB. El runner crea bases de prueba con sufijo aleatorio, ejecuta trece casos incluyendo dos sesiones concurrentes, escribe `Evidencias_h3/salida_bateria_customer_turned.txt` y elimina las bases creadas por él. El script de auditoría `25` es de solo lectura; el procedimiento de reserva solo protege al sistema cuando el backend lo adopta.

Quedan para acuerdo del equipo: definición institucional de C4, alcance evaluable de TURNED, política de no-show cuando no hay registro, una fuente de duración objetivo y la migración oficial de `Dim_Persona`. El cambio backend para impedir doble reserva y registrar `EventosEtapa` corresponde al repositorio transaccional; este repositorio no contiene ese código.
